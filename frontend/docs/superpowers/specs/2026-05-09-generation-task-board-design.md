# 2026-05-09 图片/视频生成页多任务工作台改造设计

## 背景
当前图片生成页和视频生成页都采用“左侧配置 + 右侧结果”的双栏结构，但交互仍然是单前台任务模型：

- 左侧点击生成后会进入全局生成态，出现蒙版或整体进度。
- 表单会因为正在生成而被锁定，用户无法立刻修改提示词、模型或参数继续发起下一批任务。
- 右侧结果区主要面向“本次生成结果”，不是可持续追加的任务墙。
- 进度展示是全局进度，不是每个产出物独立进度。

这与目标工作流不匹配。目标是让左侧始终保持为可操作工作台，右侧改成持续追加的任务网格，每个图片或视频卡片单独维护提交中、生成中、成功、失败和进度。

## 目标
- 将图片页和视频页改造成“可连续发起任务”的生成工作台。
- 桌面端布局调整为左侧约 2/5、右侧约 3/5，右侧展示空间更大。
- 移除全局蒙版、全局顶部进度条和“后台处理”交互。
- 左侧主按钮改为“生成新图片”或“生成新视频”。
- 右侧改为网格布局，最多每行展示 4 个产出物。
- 每个产出物单独显示进度条和百分比，进度放在卡片底部。
- 支持连续追加任务：旧任务继续轮询时，左侧仍可填写新提示词并继续提交。
- 图片页保留数量选择，一次可追加 1/2/4 张图片卡片。
- 视频页首版通过前端多次调用现有接口的方式，一次可追加多个视频卡片，不修改后端协议。

## 非目标
- 首版不做页面刷新后的任务恢复。
- 首版不引入 WebSocket 或 SSE。
- 首版不改造后端视频批量生成协议。
- 首版不将任务状态提升为全局 Pinia 状态中心。

## 用户体验设计
### 1. 布局
- 桌面端将左右区域改为更明确的宽度分配，建议使用 `grid` 实现 2:3 比例。
- 移动端继续保留“表单/结果切换”的模式，但结果区改为任务网格而不是单结果面板。

### 2. 左侧操作区
- 保留当前图片/视频各自的配置能力，例如提示词、模型、比例、尺寸、时长、参考图等。
- 图片页继续保留 `1 / 2 / 4` 数量选择。
- 视频页新增与图片一致的数量选择，首版同样提供 `1 / 2 / 4`。
- 主按钮文案分别改为“生成新图片”和“生成新视频”。
- 不再因为历史任务仍在进行中而禁用整个左侧操作区。

### 3. 右侧任务区
- 使用响应式网格展示任务卡片。
- 同屏最多 4 列，较小屏幕按 1~3 列递减。
- 新任务提交后立即插入占位卡片，让用户先看到任务已进入队列。
- 卡片底部显示独立进度条和百分比，不再显示全局“Generation progress”模块。

## 方案对比
### 方案 A：分别在两个页面内直接堆叠任务队列逻辑
- 优点：开发速度快。
- 缺点：图片页和视频页会复制大量轮询、任务状态和卡片渲染逻辑。

### 方案 B：抽离任务面板公共逻辑，由页面负责表单和提交参数
- 优点：逻辑边界清晰，图片和视频可共用任务模型、轮询和卡片 UI。
- 缺点：需要新增少量组件和一个 composable。

### 方案 C：进一步做成全局任务中心
- 优点：支持跨页面和刷新恢复。
- 缺点：本次范围过大，不适合作为首版。

结论：采用方案 B。

## 核心数据模型
右侧每个产出物统一抽象为任务卡片对象，图片与视频共用一套结构：

```js
{
  id: 'local-task-id',
  batchId: '一次点击生成对应的批次标识',
  type: 'image' | 'video',
  submitStatus: 'submitting' | 'submitted',
  status: 'submitting' | 'pending' | 'success' | 'failed',
  progress: 0,
  prompt: '',
  model: '',
  aspectRatio: '',
  imageSize: null,
  duration: null,
  generationId: null,
  resultUrl: '',
  errorMessage: '',
  createdAt: 0
}
```

说明：
- `id` 用于前端卡片唯一标识。
- `batchId` 用于识别同一次点击追加的多张卡片。
- `generationId` 在接口回执返回后绑定。
- `progress` 始终以单卡为单位维护。

## 前端结构调整
新增以下复用层：

### 1. `frontend/src/composables/useGenerationTaskBoard.js`
职责：
- 维护任务数组。
- 提供创建占位卡片、绑定任务回执、更新进度、标记成功/失败的能力。
- 为每个任务维护轮询定时器。
- 在页面卸载时统一清理定时器。

### 2. `frontend/src/components/generation/GenerationTaskGrid.vue`
职责：
- 渲染空状态。
- 根据任务数组渲染响应式网格。
- 根据类型决定图片卡或视频卡的展示方式。

### 3. `frontend/src/components/generation/GenerationTaskCard.vue`
职责：
- 展示缩略图、视频、骨架态、失败态。
- 在底部展示状态、进度条、百分比。
- 提供下载、预览、重试入口。

## 图片页实现设计
### 提交流程
1. 用户点击“生成新图片”。
2. 前端校验提示词、积分和参考图上传状态。
3. 按当前数量选择先创建 `1 / 2 / 4` 个图片占位卡片。
4. 调用现有 `generateImage(payload)`。
5. 读取返回的 `generation_id` / `generation_ids` / `generations`。
6. 将回执中的任务 ID 逐个绑定到占位卡片。
7. 每个卡片独立轮询 `getGenerationResult({ id })`，独立更新进度。
8. 成功后填入图片地址；失败则展示失败态并保留卡片。

### 状态表现
- `submitting`：刚创建占位卡片，尚未拿到接口回执。
- `pending`：已拿到 `generationId`，正在轮询。
- `success`：成功展示图片。
- `failed`：展示失败提示和重试按钮。

## 视频页实现设计
### 首版提交策略
视频接口当前是单任务接口，首版不改后端。前端按数量多次提交：

1. 用户点击“生成新视频”。
2. 前端根据数量创建 `1 / 2 / 4` 个视频占位卡片。
3. 前端循环或受控并发调用多次 `generateVideo(payload)`。
4. 每次请求成功后，将返回的 `generation_id` 绑定到对应视频卡片。
5. 每个视频卡片独立轮询 `getGenerationResult({ id })`。

### 说明
- 这样可以在不改后端协议的前提下满足“一次追加多个视频任务卡片”的需求。
- 每个视频卡片的失败或成功互不影响，不因为某个任务失败而回滚整批。

## 关键边界与禁用规则
### 1. 左侧主按钮禁用条件
主按钮只受“当前这次提交”影响，不受历史任务影响：

- 提示词为空时禁用。
- 存在参考图上传中时禁用。
- 当前批次提交请求尚未返回时禁用，防止双击重复提交。
- 当前积分不足时禁用。

### 2. 历史任务不影响新提交
- 右侧卡片仍在生成时，左侧必须保持可编辑。
- 不允许继续使用原来的全局 `generating` 来锁死整个页面。

### 3. 批量提交部分成功
- 某个卡片回执失败时，只将该卡片置为失败。
- 同批次其他卡片仍继续生成。

### 4. 页面切换与销毁
- 页面销毁时清理全部轮询定时器。
- 首版不要求返回页面后恢复当前任务墙，只保证不产生脏轮询。

## 页面状态调整
### `HomeView.vue`
- 删除全局蒙版。
- 删除右侧顶部 `Generation progress` 模块。
- 删除基于全局 `generating` 的整体 skeleton 逻辑。
- 保留左侧配置表单和图片预览上传逻辑。
- 提交逻辑改为“创建任务卡片并交给任务面板管理”。

### `VideoGenerateView.vue`
- 删除全局蒙版。
- 删除顶部进度条。
- 删除单结果视频面板模型，改为多卡片模型。
- 增加视频数量选择。

## 样式约定
- 图片卡片保持正方形。
- 视频卡片优先采用 `aspect-video`。
- 进度条固定在卡片底部区域。
- 成功态底部可展示下载按钮。
- 失败态保留错误提示与重试入口。

## 测试要点
- 图片页连续多次点击生成，旧任务不应导致新按钮被错误禁用。
- 图片页一次生成 2 或 4 张时，每张卡片都能独立显示进度和结果。
- 视频页一次生成多个任务时，每个视频卡片独立轮询且互不影响。
- 某张卡片失败时，其余卡片不受影响。
- 连续更换提示词、模型、比例后再次提交，右侧任务数据不串批。
- 页面卸载后不再继续轮询。
